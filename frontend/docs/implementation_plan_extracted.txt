SaferPath Implementation Plan Product, UX, Architecture, and Build-Prompt Blueprint Prepared from:   SaferPath.md , Version 2.0, Implementation Baseline Product direction:  Responsive Progressive Web App first; native wrapper later Recommended pilot:  One bounded campus, neighbourhood, metro corridor, or business district Document purpose:  Convert the SaferPath blueprint into an implementation-ready plan for the public landing site, traveller PWA, trusted-contact view, partner portal, operational dashboards, APIs, data model, testing, and phased front-end/back-end build prompts. 1. Executive implementation decision SaferPath should be built as a  privacy-first, time-aware route-context product , not as a generic emergency app and not as a static “safe route” calculator. The primary journey is: Understand SaferPath → optionally create an account → enter a route → choose a travel time → compare two or three route options → inspect evidence and uncertainty → choose a route → optionally start a time-limited check-in. The first release must make one behavior unmistakable:  the same route can have different contextual evidence at 6:00 p.m., 9:00 p.m., and 11:30 p.m., and the product explains why. The implementation must not describe a street as objectively safe or unsafe. It must use neutral labels such as  stronger contextual support ,  good context ,  mixed context ,  caution segment ,  limited data ,  stale evidence , and  unknown . 1.1 What belongs in the first build The first demonstrable build should include: A public landing and explanation site. Welcome, language, accessibility, privacy, and consent screens. Optional account registration and login. Home and route search. Origin, destination, travel mode, and departure/arrival-time selection. Two or three seeded route alternatives for one bounded pilot area. Segment-level context for lighting evidence, activity, isolation, help points, route continuity, reports, freshness, and confidence. A “Why this route?” explanation drawer. A text alternative to the map. Structured route-context reporting. Report status and privacy controls. Optional simulated check-in and deviation prompt, clearly labelled as a pilot/demo capability. Accurate emergency handoff language. Loading, empty, insufficient-data, stale-data, offline, denied-permission, and failure states. A small moderation/data-quality fixture dashboard sufficient to demonstrate governance. 1.2 What should not block the first build The following must remain outside the critical path unless partner access already exists: Direct Uber, Ola, or Rapido booking or trip-status APIs. Official police or ambulance dispatch integrations. Nationwide crime prediction. Continuous background tracking by default. Permanent individual location histories. LLM-based safety decisions. A national complaint-management system. Native applications. Real production notifications. Large-scale partner administration. 1.3 Important adjustment to the requested registration fields The requested fields—name, home address, company address, company name, email, phone, emergency contact, student/employee status, college or workplace details, routine timing, distance, and regular destinations—should  not all be mandatory at registration . Use a progressive model: Information When to collect Why Default treatment Display name Optional account setup Personalise the experience Optional; allow pseudonym Email or phone Account verification and recovery Authentication One verified identifier required for a full account Home address Only if user chooses to save a frequent origin Faster route planning Store as a private saved place, not public context Company/college name Only for an opted-in institutional pilot or personal shortcut Institution-specific features Optional; never required for route planning Company/college address Only when saving a frequent place Route shortcut and pilot context Optional; coarse display and protected storage Emergency/trusted contact Only before check-in or if user chooses setup Time-limited journey sharing Optional; never silently notify anyone Work/student/daily-use profile During optional personalisation Tailor defaults and route suggestions Skippable and editable Regular destinations When user chooses saved places Convenience Optional; each place deletable Usual time When user creates a routine Prefill route time Optional; editable and non-sensitive by default Distance between places Calculate from saved places when needed Route planning Do not ask if it can be derived Continuous location Only for an explicitly active trip Trip support Off by default; time-limited The product should explain this clearly:  “You can use route planning without sharing your home, workplace, college, contacts, or continuous location.” 2. Product surfaces and navigation model SaferPath has four product surfaces and six operational dashboard areas. 2.1 Surface A: Traveller PWA Primary navigation for an authenticated traveller: Home  — route search and recent/saved places. Trips  — current and past trip sessions, if enabled. Reports  — submitted report status and report privacy controls. Help nearby  — verified support points around the selected route or current manual location. Settings  — profile, language, accessibility, notifications, contacts, privacy, and account controls. On mobile, use a four- or five-item bottom navigation. Keep  Home  visually primary. During an active trip, replace or augment navigation with a persistent  Active trip  status control. 2.2 Surface B: Trusted-contact view A separate read-only page accessed through an authenticated, expiring, scoped grant. It may show only: traveller-approved journey status; planned arrival; last update time; route or area detail only if explicitly shared; approved contact actions; stale/revoked/expired state. It must never expose a full account, report history, private evidence, or permanent route history. 2.3 Surface C: Partner/organisation portal Tenant-scoped portal for campuses, employers, city programmes, NGOs, and approved safety partners. It manages: verified help points; opening status and verification expiry; partner tasks; aggregate patterns; approved operational updates; tenant settings and access. Partners must not suppress negative public context or obtain individual histories without explicit lawful consent. 2.4 Surface D: Public landing and onboarding site Public pages explain: the problem; the time-aware route-context solution; the evidence model; limitations; privacy commitments; accessibility commitment; pilot/partner model; contact or pilot-interest intake. The public site must not expose live locations, individual reports, or operational data. 3. Visual and content direction The interface should feel  calm, precise, protective, and non-alarmist . 3.1 Visual system Warm neutral surfaces:  background and cards. Deep ink:  primary text and trust-oriented headings. Mint/teal:  stronger contextual support and verified evidence. Amber:  mixed or limited confidence. Coral:  caution and emergency actions only. Monospaced text:  timestamps, freshness, source status, and system state. Display serif:  major product statements and public landing hero. Readable sans-serif:  all controls, form fields, and body copy. No colour-only meaning:  every state has text, icons, and accessible labels. 3.2 Content rules Use: “context” instead of “safety score”; “evidence” instead of “proof”; “caution segment” instead of “unsafe street”; “limited data” instead of implying a positive or negative condition; “official emergency service” instead of implying SaferPath itself responds; “last verified” and “confidence” beside every relevant signal group. Never use: “guaranteed safe”; “crime probability”; “this street is dangerous”; “help is on the way” unless an official service has confirmed it; “we are tracking you” as a default statement; deceptive calculator or concealment claims. 3.3 Persistent global components Build these once and reuse them: App header with logo, page title, account menu, and emergency/help entry. Offline/stale banner. Consent-status indicator where relevant. Bottom navigation for the traveller PWA. Modal/drawer shell with focus trapping and Escape support. Toast/status announcement region for screen readers. Evidence chip. Freshness label. Confidence label. Context band. Route card. Text route summary. Empty, loading, stale, error, and insufficient-data patterns. Confirmation sheet for irreversible or privacy-sensitive actions. Emergency action sheet with clear handoff boundary. 4. PUB-01 — Landing page Goal:  Make the product understandable in ten seconds and credible in one minute. Hero content: Headline:  “Choose your route with more context.” Supporting statement: “SaferPath shows how route evidence changes with the time you travel, including lighting evidence, activity, isolation, help points, reports, freshness, and confidence.” Primary CTA:  Try route planning . Secondary CTA:  See how it works . Trust note: “SaferPath does not certify a street as safe, predict crime, or replace emergency services.” Hero visual:  A route comparison at 6:00 p.m., 9:00 p.m., and 11:30 p.m. Use a static seeded illustration or interactive demo with no live location. Sections: The context gap between fastest route and usable route. The Time-Window Safety Lens. Evidence categories. A three-step product flow: enter route, inspect context, choose with control. Privacy commitments. Accessibility commitments. Pilot/partner invitation. Emergency limitation statement. Footer with privacy, terms, source register, and contact. Required states: If JavaScript is unavailable, show a static explanation and link to route planning. If the demo fixture fails, show an accessible static route comparison. Contact form errors must be field-specific and must not expose submissions publicly. Analytics:   PUBLIC_LANDING_VIEWED ,  PUBLIC_DEMO_STARTED ,  PUBLIC_HOW_IT_WORKS_VIEWED ,  PUBLIC_PILOT_CTA_CLICKED . PUB-02 — How it works Explain the distinction between routing and context enrichment. Show that the routing provider supplies feasible alternatives and the Safety Context Engine joins each segment with time-aware evidence. Include a visual timeline of expected segment arrival times. The page must explain: time window; segment evidence; freshness; confidence; missing data; neutral context bands; user choice. PUB-03 — Limitations and emergency boundaries Use direct copy: “SaferPath provides route context and optional journey support. It does not dispatch police or medical services, certify a route as safe, detect crimes, guarantee rescue, or confirm that an emergency service has accepted a case.” Show official emergency options for the configured region. Clearly distinguish: displaying an official number; opening a call or deep link; submitting a handoff request; receiving confirmation from an official system. Only the final state may say that an official service confirmed receipt, and only if an integrated source actually confirms it. PUB-04 — Privacy commitment Explain in plain language: route planning can work without active-trip tracking; location is off by default outside an active trip; saved places are private; trusted-contact access is scoped and expires; public reports are coarse-located and moderated; private evidence is separately permissioned and retained until expiry; users can revoke, export, correct, or request deletion. Include a privacy “what we do not do” section: do not sell individual location histories; do not silently notify contacts; do not expose exact private incident locations; do not use one report to permanently label a street. AUTH-01 — Welcome and consent Layout:  calm introduction, not a legal wall of text. Content: “SaferPath helps you compare route context at the time you expect to travel.” “It does not guarantee safety or replace emergency services.” “You can plan a route without enabling active-trip tracking.” Link to privacy summary and full policy. Actions: Continue without account. Create an account. Sign in. Choose language. Open accessibility setup. Consent behavior:  Record only the acceptance of the current product disclosure if the user proceeds. Do not infer location or contact consent. AUTH-03 — Login Support either: email plus password; or phone/email one-time code. For MVP, a single method should be implemented cleanly rather than two incomplete methods. Recommended: email plus one-time code for reduced password risk. Fields:  email or phone, code, resend code, change identifier. States:  invalid identifier, expired code, too many attempts, offline, unverified account, session restored, account restricted. Privacy:  Do not reveal whether an arbitrary email or phone is registered. Use neutral messages. AUTH-04 — Registration Minimum fields: preferred display name or pseudonym; email or phone; verification step; country/region only if required for emergency information; acknowledgement of product limitations. Optional after verification: traveller type: student, employee, daily-use traveller, prefer not to say; saved places; trusted contact; notification preference. Do not require:  home address, employer address, college address, emergency contact, continuous location, or routine schedule. Copy:  “You can add these later. Route planning does not require them.” AUTH-06 — Optional traveller profile Present four cards: Student  — “Save a campus or hostel as a frequent place and optionally add class or commute timing.” Employee  — “Save a workplace and optionally add shift timing or a regular commute.” Daily-use traveller  — “Save common places and preferred travel context.” Skip for now  — “Use SaferPath without a personal routine profile.” Each card must explain what data is saved and how to delete it. Avoid collecting job title, salary, manager, or company directory details unless a specific institutional pilot requires them. AUTH-11 — Location permission education Use two separate explanations: Route-planning location:  used to prefill current origin if enabled; manual origin remains available. Active-trip location:  used only during an explicitly started trip; off by default outside the trip. The browser permission request must follow the explanation, not precede it. TRV-01 — Home/route search Primary area:  origin and destination fields. Controls: use current location, if permission exists; type a place; choose from saved private places; pick on map; swap origin/destination; departure/arrival-time button; travel mode button; preference button; compare routes. Supporting copy:  “Context is shown for the expected time you reach each segment.” Empty state:  “Enter where you are starting and where you are going.” Recent searches:  Store only under the product’s short-retention policy; offer clear/delete controls. TRV-02 — Place search and map picker Allow typed search and coarse manual selection. If geocoding fails, the user can select a pilot-area location from a map or a text list. Show privacy notice before saving a place. Do not expose exact saved places in public or partner views. TRV-03 — Date/time and arrival mode Provide three modes: Leave now. Leave at a selected date/time. Arrive by a selected date/time. Display the selected local timezone and a human-readable summary. Explain that context is evaluated using expected arrival time per segment, not only the start time. TRV-04 — Travel mode and route preference Travel modes for MVP: walking; mixed/last-mile walking. Preferences: fastest; stronger lighting evidence; more active frontage; more help points; lower transfers; more accessible continuity; lower cost, if cost fixtures exist. Do not make “safest” the preference label. The product must not imply an objective safety ranking. TRV-05 — Route comparison This is the highest-priority product screen. Header:  selected route time, mode, and “change time” control. Main layout: map with route alternatives; accessible legend; route cards below or beside the map; text route summary toggle; last-mile highlight; report and help actions. Each route card contains: route label: A, B, or C; duration and distance; walking distance/time; selected preference match; context band; strongest positive signal; strongest caution segment; help-point count and nearest distance; report freshness; confidence label; “Why this route?” button; “Select route” button. Required example behavior:  At 6:00 p.m., Route A may be faster. At 9:00 p.m., Route B may have stronger activity evidence. At 11:30 p.m., Route B may be longer but have stronger lighting evidence and verified help points. The changes must come from seeded fixtures and be deterministic. No-data behavior:  Show the route options if geometry exists, but replace positive claims with  limited data . Explain which signal groups are missing. Never display:  one opaque numeric safety score, green/red route badges without text, “safe/unsafe” labels, or a route guarantee. TRV-06 — Route explanation drawer Open from a route card. Use a clear evidence hierarchy: Why this route may fit your preference. What requires attention. What is unknown or stale. How the context was calculated. Which segment is affected. Example content: Route B has stronger contextual support at 11:30 p.m. It has two verified help points within 250 metres and stronger lighting evidence. Route A is four minutes faster but includes 700 metres with incomplete lighting data and two independent time-matched reports. Confidence is medium because one lighting source was last verified 12 days ago. Every evidence item shows: feature group; affected segment; observation time or validity window; source class; freshness; confidence contribution; limitation. TRV-07 — Segment detail Show a segment timeline and details for: lighting evidence; activity nearby; isolation indicators; help points; reports; route continuity/accessibility; connectivity if relevant to active trip; freshness and confidence. Use approximate locations for public reports. Show report count and diversity only when thresholds permit. Never expose exact private incident coordinates. TRV-08 — Full text route summary The text alternative must be a real alternative, not a small caption. It should contain: ordered segments; distance and estimated time; crossing and continuity notes; context band per segment; positive/caution/unknown evidence; help points; freshness and confidence; selected route action. REP-01 to REP-06 — Structured report flow Supported categories:  streetlight not working, isolated stretch, unsafe waiting point, blocked or broken path, help point unavailable, harassment or suspicious behaviour observed, road/transport issue, other structured hazard. Flow: Explain that a report adds context and is not an emergency dispatch. Select category. Select a coarse route segment or manual map area. Select observed time. Add optional short note. Add optional evidence only if safe and consented. Explain public/private treatment and retention. Review and submit. Show pending status, report token, expiry, and deletion/correction path. Anti-gaming behavior:  rate limit, pseudonymous token, duplicate clustering, time and reporter diversity, expiry, human moderation for high-impact clusters. Submission confirmation:  “Your report was received for review. It has not yet changed public route context.” TRIP-01 — Check-in setup This is optional and must be clearly separated from route planning. Fields: planned arrival; selected route; sharing: no contact, selected trusted contact, approved scope; mode: manual, timed prompt, deviation prompt; active-trip location consent; retention boundary; notification preference. Pre-submit summary: who can see the trip; what they can see; when access expires; what SaferPath does not guarantee; stop/revoke controls. TRIP-02 — Active trip Show: active status; planned arrival; next check-in or prompt time; last update time; network and battery status, if available; sharing state; stop trip; confirm okay; find help; official emergency option. Do not show a constantly updating map by default. The minimum necessary status is preferable. Actions: I’m okay; continue trip; notify selected contact; stop trip; find help nearby; call official emergency service. TRIP-05/TRIP-06 — Help nearby and help-point detail Each point shows: category; distance; open/closed/unknown; accessibility; last verification; availability confidence; call/contact method; navigate; share, if user chooses. Stale points must be hidden or marked limited data. A partner-sponsored point must be visibly disclosed. SET-04 — Privacy centre Sections: Current consent grants. Active sharing grants. Saved places. CON-02 — Trusted-contact trip view Show only approved scope: traveller display name or chosen label; journey status; planned arrival; last update; live/recent/stale state; approved contact actions. OPS-01/OPS-02 — Moderation Queue columns: report category; coarse segment; observed time; submitted time; duplicate cluster; reporter diversity; confidence; evidence access status; expiry date; moderation status. First-time onboarding flow in detail 6.1 Recommended onboarding sequence Public landing page. Try route planning or create an account. Welcome and limitation disclosure. Language and accessibility preferences. Login/registration. Identifier verification. Optional traveller type selection. Optional student/employee/daily-use profile. Optional saved places. Optional trusted contact. Location permission education. Emergency region information. Setup complete. Home route search. 6.2 Progressive disclosure rules Do not ask for a home address before the user wants to save “Home.” Do not ask for a college or company name merely to compare routes. Do not ask for an emergency contact until the user chooses check-in or explicitly opens contact setup. Do not ask for active-trip location permission until the user starts a trip. Do not infer that student/employee status grants access to an institution. Do not use company/college affiliation for ranking without a documented pilot purpose and consent. Let the user skip every optional personalisation step. Make every optional field editable and deletable. 6.3 Profile branching logic If user selects Student:   offer college and residence as private saved places   offer routine time and days   derive distance and ETA from selected places   offer accessibility preferences If user selects Employee:   offer workplace and drop-off as private saved places   offer fixed/shift/variable schedule   offer routine time and days   derive distance and ETA from selected places If user selects Daily-use traveller:   offer frequent places and preferred travel modes   offer optional time windows If user selects Skip:   go directly to route planning 6.4 Privacy copy for profile collection Use a short explanation before each branch: “This information is optional. It helps prefill your routes and routine preferences. It is not required for route planning, is not published to other users, and can be deleted from Privacy Centre.” 7. Every trip event, notification, and sharing grant stores the consent version under which it was created. 9. Safety Context Engine implementation The routing provider creates feasible alternatives. The Safety Context Engine enriches route segments and ranks alternatives according to the selected preference. 9.1 Feature groups Feature group Example fields User-facing label Lighting coverage, last verified, confidence Lighting evidence Activity open frontage, transit activity, time window Activity nearby Help points count, distance, operating status, verification Help nearby Reports category, recency, diversity, corroboration Recent context reports Isolation continuity, inactive frontage, waiting complexity Isolation Infrastructure footpath, crossings, accessibility, blocked path Route continuity Freshness age, expiry, source refresh Data freshness Connectivity GPS/network confidence Trip reliability 9.2 Transparent prototype ranking Use the following only as an internal prototype ranking mechanism: context_fit =   0.25 * lighting_evidence + 0.20 * activity_evidence + 0.15 * help_point_access + 0.15 * report_context + 0.10 * route_continuity + 0.10 * transit_or_partner_support + 0.05 * accessibility_fit Do not expose this as one “safety score.” Display component evidence, confidence, and missing data instead. 9.3 Confidence Confidence must consider: source quality; freshness; segment coverage; corroboration; reporter diversity; consistency; expiry; uncertainty. Final implementation rule Build the route-context decision and its explanation before building another safety module. A successful SaferPath implementation is not the one with the largest number of safety features. It is the one that lets a traveller compare a route at different times, see the relevant segment and evidence, understand freshness and uncertainty, choose for herself, and retain control over sharing and tracking.
